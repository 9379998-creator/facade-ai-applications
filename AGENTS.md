# Инструкции и правила для ИИ-агентов (AGENTS.md)

Добро пожаловать в репозиторий `facade-ai-applications`. Любой автономный или полуавтономный агент (Antigravity, Cursor, Codex, Claude, и др.), работающий в этом репозитории, **обязан строго следовать следующим правилам**:

## 1. Базовые правила ветвления и Git
1. **Никогда не коммитить напрямую в `main`**. Все изменения делаются только в тематических ветках (`chore/*`, `feat/*`, `fix/*`, `docs/*`) и вливаются через Pull Request.
2. **Один Pull Request — одна понятная задача**. Не смешивать архитектурные изменения с правками стилей или несвязанными текстами.
3. **Никакого `git push --force`** в публичные и разделяемые ветки. Никогда не переписывать историю Git.
4. **Не объединять (merge) Pull Request самостоятельно**, если нет явной команды владельца проекта. Оставлять PR в статусе `Draft` или открытым для ревью владельца.

## 2. Перед началом любой работы обязательно изучить:
- `docs/00-project-charter.md` — Устав и цели проекта;
- `docs/02-roadmap.md` — Текущий статус дорожной карты;
- `docs/03-requirements.md` — Функциональные и нефункциональные требования;
- `docs/05-data-policy.md` — Строгая политика защиты данных.

## 3. Политика данных и конфиденциальность
5. **Категорический запрет на реальные конфиденциальные данные**: Никаких реальных коммерческих смет, реальных договоров, клиентских чертежей, персональных данных (ФИО, телефонов, личных email), ИНН, банковских реквизитов.
6. **Никаких секретов**: Не коммитить API-ключи, токены, пароли, приватные ключи, абсолютные пути операционной системы с именами пользователей.
7. **Синтетический объект**: Все демонстрации проводятся исключительно на вымышленном синтетическом объекте «Северный порт».

## 4. Честность контента и статусов
8. **Не придумывать подтверждённые показатели**: Никогда не писать «система экономит 40% бюджета» или «находит 99% ошибок», если нет документированного замера на эталоне.
9. **Строго соблюдать статусы**:
   - `WORKING` — только для функций, реально работающих в коде и покрытых тестами.
   - `PROTOTYPE` — для интерактивных кликабельных макетов без полного цикла.
   - `CONCEPT` — для целевых идей и описаний алгоритмов.
   - `TBD` — для всех параметров, требующих уточнения.
10. **Не выдавать прототип за готовую промышленную систему**.
11. **При любой неопределённости ставить отметку `TBD`**.

## 5. Архитектурная дисциплина и зависимости
12. **Отделение контента от представления**: Тексты и модели данных хранятся в типизированных файлах JSON/TS в каталоге `content/`, а не хардкодятся в React-компонентах.
13. **Не добавлять новые библиотеки** без исчерпывающего обоснования и проверки влияния на размер бандла.
14. **Не добавлять серверный бэкенд** или базы данных без отдельного архитектурного решения (ADR).
15. **Не копировать сторонние репозитории** (включая исходный код Launcher).
16. **Не проводить массовый рефакторинг** без отдельного задания.
17. **Не удалять согласованный контент** без разрешения владельца.

## 6. Качество и верификация кода
18. **После любых изменений запускать полный набор проверок**:
    `npm run validate` (lint, typecheck, unit tests, validate:content, scan:sensitive, check:large-files, build).
19. **Не подавлять ошибки тестов и линтера**. Запрещено использовать заглушки, пустые проверки или необоснованный `test.skip`.
20. **Проверять мобильный (375px) и настольный режимы**, следить за отсутствием горизонтального скролла.
21. **Соблюдать стандарты доступности (A11y)**: семантический HTML, клавиатурная навигация, видимый фокус.
22. **Обновлять `CHANGELOG.md`** при любых изменениях, видимых пользователю.
23. **Обновлять документацию в `docs/`** при изменении архитектурных решений.
24. **Объяснять все результаты владельцу простым, понятным русским языком**.
